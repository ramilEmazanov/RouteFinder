# RouteFinder — поиск транспортных маршрутов на C++

Консольное приложение для поиска маршрутов между городами через API Яндекс Расписаний. Пользователь задаёт направление, дату, тип транспорта и возможность пересадки, а приложение показывает подходящие варианты с деталями каждого участка пути.

Проект выполнен в рамках лабораторной работы № 7 в ИТМО, посвящённой работе с внешними библиотеками. Реализация объединяет HTTP-запросы, обработку JSON, локальное кэширование и тестирование бизнес-логики с подменой внешних зависимостей.

**Ключевое архитектурное решение — трёхслойная архитектура:** представление (Presentation), бизнес-логика (Business Logic) и доступ к данным (Data Access). Слои разделяют ввод и вывод, правила обработки запросов и взаимодействие с API и кэшем.

**Стек:** C++23 · CMake · CPR · nlohmann/json · GoogleTest · Google Mock · CTest

## Возможности

- **Поиск между городами:** направление и дата задаются пользователем в интерактивном режиме.
- **Прямые маршруты и одна пересадка:** из ответа API извлекаются варианты без пересадок либо с одной пересадкой, включая сочетания разных видов транспорта.
- **Фильтрация по транспорту:** поезд, самолёт, автобус, электричка, водный транспорт или вертолёт. При выборе типа транспорта проверяется каждый участок маршрута.
- **Подробный вывод:** станции отправления и прибытия, время с часовым смещением, перевозчик, длительность участков и сведения о пересадке.
- **Несколько запросов за запуск:** меню позволяет повторять поиск, открывать справку и завершать работу.
- **Локальный кэш:** повторный запрос может обслуживаться без обращения к API; результаты сохраняются между запусками.
- **Справочник городов:** названия преобразуются в коды Яндекса с использованием локального JSON-справочника.

Наличие маршрутов определяется данными внешнего сервиса. Приложение получает готовые варианты от API и фильтрует их на своей стороне.

## Трёхслойная архитектура

Приложение организовано в три слоя с отдельными обязанностями:

| Слой | Компоненты | Ответственность |
| --- | --- | --- |
| **Представление — Presentation** | `CLIParser`, `RoutePrinter`; каталог `lib/presentation/` | Интерактивное меню, проверка формата ввода и отображение маршрутов |
| **Бизнес-логика — Business Logic** | `MainService`, интерфейсы `IRouteRepository` и `ICitiesDict`; каталог `lib/business_logic/` | Обработка запроса, преобразование названий городов через справочник и фильтрация результатов |
| **Доступ к данным — Data Access** | `YandexRepository`, `CacheRepository`, `Cache`, `YandexCitiesDict`, JSON-обработчики; каталог `lib/infrastructure/` | HTTP-запросы, получение и преобразование данных, файловое хранение и кэширование |

Общие модели вынесены в `lib/structures/`. В `main.cpp` создаются конкретные реализации и передаются зависимости: бизнес-логика получает источники данных через интерфейсы, а CLI обращается к сервису для выполнения поиска.

Такое разделение позволяет менять формат представления результатов отдельно от правил поиска, подключать другой источник маршрутов через `IRouteRepository` и тестировать `MainService` без сетевых запросов. Кэширование подключается на уровне доступа к данным через обёртку `CacheRepository`.

### Взаимодействие слоёв

```text
Интерактивный ввод — CLIParser
            ↓
MainService — преобразование названий городов в коды
            ↓
CacheRepository
    ├── актуальные данные → локальный кэш
    └── нет данных → YandexRepository → HTTP API → разбор JSON
            ↓
MainService — фильтрация маршрутов
            ↓
RoutePrinter — вывод результата
```

### Слой представления

`CLIParser` собирает параметры поездки и проверяет формат ввода. `RoutePrinter` отвечает за отображение маршрутов, участков пути и пересадок. Цикл меню в `main.cpp` связывает ввод пользователя с вызовом `MainService` и выводом результата.

### Слой бизнес-логики

`MainService` принимает запрос, получает коды городов через `ICitiesDict` и обращается к `IRouteRepository`. Полученные маршруты фильтруются по разрешению пересадок и типу транспорта.

Сервис зависит от интерфейсов, поэтому в тестах реальные источники данных заменяются mock-объектами. Модели `RouteRequest`, `Route`, `Segment` и `TransferInfo` описывают запрос, маршрут, отдельный участок поездки и пересадку.

### Слой доступа к данным

`YandexRepository` формирует запрос к API, проверяет сетевые ошибки и HTTP-статус, после чего передаёт JSON в `APIJsonExtracter`. Разбор прямых маршрутов и маршрутов с пересадкой вынесен в отдельные методы.

`CacheRepository` реализует тот же интерфейс `IRouteRepository` и оборачивает источник данных: сначала проверяет кэш, а при отсутствии результата обращается к API и сохраняет ответ. Это позволяет подключить кэширование без изменения `MainService`.

### Кэширование

| Данные | Время жизни | Хранение и ограничение |
| --- | --- | --- |
| Результаты поиска | 1 час | В памяти и в `cache.json`; по умолчанию до 10 записей |
| Справочник городов | 7 дней | Файл `cities_dict.json` |

Ключ кэша маршрутов включает направление, дату, фильтр транспорта и разрешение пересадок. При превышении лимита удаляется запись с наиболее старым временем сохранения. Чтение записи не обновляет её возраст.

Кэш маршрутов загружается при создании `Cache` и записывается на диск в деструкторе. Просроченные записи удаляются при загрузке, чтении и добавлении данных; некорректный JSON кэша приводит к его очистке в памяти.

## Сборка и запуск

Понадобятся Git, CMake версии 3.23 или новее, компилятор с поддержкой C++23 и доступ к сети для первоначальной загрузки зависимостей через FetchContent. Команды ниже рассчитаны на macOS/Linux и выполняются из корня проекта:

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build --target labwork7
./build/labwork7 YOUR_YANDEX_RASP_API_KEY
```

Имя исполняемого файла в текущей конфигурации — `labwork7`. Ключ API передаётся первым аргументом; параметры поездки вводятся после запуска.

**Особенность текущей настройки:** аргумент командной строки используется для поиска маршрутов. Загрузчик справочника городов `RawCitiesJsonRequester` использует отдельный ключ, заданный в `lib/infrastructure/stations_parser/stations_parser.cpp`. Для запуска со своими учётными данными требуется настроить и этот источник; его перевод на общий механизм передачи ключа остаётся направлением развития.

Файлы `cache.json` и `cities_dict.json` создаются в корне исходного проекта: путь фиксируется при сборке через определение `ROOT`.

## Пример работы

После запуска появляется меню:

```text
1. Новый запрос
2. Помощь
3. Выход
>
```

Для поиска выберите `1` и заполните поля, например:

```text
Введите город отправления: Санкт-Петербург
Введите город прибытия: Казань
Введите дату (YYYY-MM-DD): 2026-12-01
Введите тип транспорта (train/plane/bus/suburban/water/helicopter) или оставьте пустым:
Разрешить до одной пересадки? (yes/no): yes
```

Пустой фильтр транспорта позволяет искать варианты с разными видами транспорта. Для обратной поездки создайте новый запрос, поменяв города местами.

Названия городов должны соответствовать справочнику. CLI проверяет непустые поля, шаблон даты `YYYY-MM-DD`, допустимый тип транспорта и ответы `yes/no`. При отсутствии подходящих вариантов выводится `No routes found`.

## Тестирование

В проекте 23 теста в шести группах:

- **Бизнес-логика:** фильтрация пересадок и транспорта, неизвестные города и ошибки репозитория.
- **Репозиторий с кэшем:** получение сохранённого результата без вызова API, обращение к источнику при промахе и обработка исключений.
- **Кэш:** запись, чтение, отсутствие ключа и ограничение количества записей.
- **Разбор маршрутов:** прямые рейсы, одна пересадка, отсутствие результатов и некорректная структура JSON.
- **Справочник городов:** преобразование ответа API, пропущенные поля и запись справочника в файл.
- **CLI и вывод:** повторный ввод после ошибок и отображение маршрутов либо отсутствия результатов.

Сетевые зависимости в тестах сервиса и репозитория заменены Google Mock; JSON-обработчики проверяются на подготовленных данных.

```bash
cmake --build build --target labwork7_tests
ctest --test-dir build --output-on-failure
```
